# Technical Assessment: AI Proposal Triage Design

## 1. AI vs. Rules
* **AI Steps:** 
  * **Structured Data Extraction:** LLMs excel at reading unstructured proposal text (PDFs) and mapping facts into a deterministic, strongly-typed JSON schema based on dynamically provided admin criteria.
  * **Qualitative Scoring:** LLMs score nuanced criteria ("Team and approach", "Relevant experience") against dynamic criteria guidelines and provide justifications.
* **Rule/Code Steps:**
  * **Prompt Injection & Adversarial Sanitization:** Regex and deterministic filtering scan extracted text for prompt injections (e.g., hidden instructions in Appendix C).
  * **Mandatory Criteria Evaluation:** Deterministic boolean logic (`IF electrical_licence == False THEN status = Ineligible`).
  * **Weighted Math & Final Scoring:** Normalization formulas (e.g., min-max pricing curves, warranty year conversions) and final weighted summation ($Score = \sum Weight_i \times Subscore_i$) are strictly executed in code.
* **Rationale:** Language models are non-deterministic and weak at math or strict boolean gates. AI is reserved for semantic extraction and qualitative assessment, while business rules, compliance gates, and mathematical aggregation remain 100% deterministic code.

## 2. Consistency and Explainability
* **Repeatability:**
  * Extraction and qualitative scoring calls use `temperature: 0.0` with standard JSON schema enforcement (Structured Outputs / JSON Mode).
  * Evaluated criteria parameters are stored in a deterministic database record upon extraction.
* **Explainability:**
  * Every score generated by the AI requires a structured `reasoning` string detailing specific facts extracted from the text.
  * The frontend UI renders a breakdown card showing: Raw Text Excerpt $\rightarrow$ Extracted Metric $\rightarrow$ Rule Calculation/LLM Score $\rightarrow$ Sub-score Breakdown.

## 3. Human in the Loop & Audit Logging
* **Human Checkpoints:**
  * **Pre-Ranking Approval:** The reviewer must inspect and verify the AI-extracted metadata (e.g., cost, timeline, licence status) before trigger-ranking.
  * **Flag Resolution:** Any proposal triggering security flags (e.g., injection attempts, missing critical fields) is set to `flagged` for mandatory human override.
  * **Final Award:** The system only presents ranked recommendations; award decisions require explicit human authorization.
* **Audit Logging:**
  * All admin criteria version IDs, raw PDF hashes, extracted JSON schemas, LLM prompts/responses, override logs, and final reviewer signatures are stored immutably in an audit database table.

## 4. Handling Changing Criteria
* **Versioned Pipeline Strategy:**
  * Admin criteria configurations are version-controlled (e.g., `Criteria_v1.0`).
  * Existing evaluations remain tied to the criteria version active at the time of scoring (`evaluated_with_version: v1.0`).
  * If an admin updates criteria or weights, existing proposals move to a `Re-evaluation Required` state. The user can choose to keep historical rankings or trigger an automated re-score using the new criteria version baseline.

## 5. Risks and Safeguards
* **Prompt Injection / Manipulation (e.g., Proposal C Appendix C):** Extracted text is sanitized via strict input boundary delimiters (`<proposal_text>`) and systemic instruction layering. Structural metadata is extracted prior to scoring, rendering indirect instructions inert.
* **Hallucinations & Made-up Facts:** Extracted data must include an exact verbatim quote string (`quote_source`). If the citation cannot be verified in the source text, the field defaults to `null` and flags the document.
* **Extraction Errors:** Low-confidence extractions automatically mark the proposal as `flagged` for manual reviewer verification.
* **Cost & Latency:** Small, optimized models (e.g., GPT-4o-mini / Claude 3 Haiku) are used for single-pass extraction, caching system prompts for administrative criteria.
